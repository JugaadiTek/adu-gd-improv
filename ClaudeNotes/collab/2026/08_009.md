## Verticality - and a real sim bug this surfaced (not just tuning)

The literal ask was "give the course more verticality." First attempt
(raising `CoursePath.MAX_CENTER_Y` alone, 3.2 -> 4.6) did **nothing** -
measured the actual generated course and it topped out around y=1.06
regardless, because `slope_climbing` was picked with a flat 50/50 coin flip
every 2-4 pieces: a random walk in height that statistically rarely
sustains a real climb. The ceiling was never the bottleneck.

Fixed the actual mechanism: added `CoursePath.CLIMB_PERSISTENCE` (0.70) -
each slope-interval change now has a 70% chance of *continuing* the
previous climb/descend direction instead of a coin flip, which is what
actually produces a sustained "climb to a high point" instead of gentle
up-down jitter. Real result: max course height went from **y=1.06 to
y=1.82** (+72%) for the actual shipped seed (1337 - `CoursePath.generate()`
always uses this default, so every playthrough is the same course; this
isn't a statistical average, it's what players will actually see).

Getting there exposed a genuine bug in the playability sim, not the game
itself - worth recording in detail since it's exactly the kind of thing
this project's own testing philosophy says to expect
(`test_runner.gd`'s class comment: "a stuck-forever pattern in this sim is
more often a missing case in the sim's own decision logic than 'the course
needs to be easier'" - that call was right again):

1. At higher persistence values the sim got stuck retrying an identical
   failing jump shot for 40+ consecutive strokes, position frozen to 6
   decimal places. Added `SIM_DEBUG`-gated per-stroke logging
   (`test_runner.gd`, env var gated, no output normally) to see it -
   turned out the ball wasn't wedged in geometry at all: it was
   **respawning to an earlier checkpoint after a failed jump, then
   re-aiming the exact same failing jump forever**, because
   `_nearest_piece_index_from`'s "only ever search forward, never regress"
   guard (added earlier specifically so the winding path passing near its
   own earlier stretch wouldn't confuse it) had too generous a reset
   condition (`dist_to_progress <= 6.0`) - a respawn to a checkpoint well
   within 6m of the stale tracked piece never triggered the reset, so the
   forward-only search window couldn't see the piece the ball had actually
   respawned onto. **Fixed**: also run an unrestricted nearest-piece search
   each stroke, and if it finds a piece genuinely *behind* progress and the
   ball is actually resting close to it (a real regression, i.e. a
   respawn - not just the path passing near old geometry while still net
   moving forward), trust it and let progress regress.
2. With that fixed, the sim got past the jump but then stalled differently
   on a short, steep uphill hop - loft-only compensation (added first, see
   below) got it moving but left it oscillating near the target for 60+
   strokes without quite landing. Needed a modest power floor too, not
   loft alone.
3. Also added general uphill-terrain compensation to the sim's swing
   heuristic: it previously scaled power purely off flat horizontal
   distance, with no notion of grade at all - fine while height changes
   were incidental, not fine now that a real sustained climb is possible.
   `loft = maxf(loft, 0.18 + height_diff*0.6)` and
   `power = maxf(power, 1.4 + height_diff*2.2)` when the lookahead target
   is uphill. (First attempt boosted power much more aggressively and
   *overshot* the target platform instead of undershooting - worth noting
   since it's the opposite failure mode from every other "stuck" case
   logged in this project so far, and boosting power blindly made it
   *worse*, not better.)

Final playability result: **109 strokes** (budget 120) - real margin, not
a hair's-breadth pass; tried pushing `CLIMB_PERSISTENCE` further (was
briefly at a config that only just passed at 119/120) and backed off
specifically to keep this margin rather than ship something fragile.

## Driver arc shot

`ClubController.WHACKERS`' Driver (Toothbrush) `loft_factor`: 0.34 -> 0.52.
Note this doesn't touch the playability sim at all - confirmed the sim's
jump/uphill swings use their own hardcoded loft values (0.4, and the new

real-gameplay-only and untested by the automated suite (consistent with
how the rest of the per-whacker tuning has always been - `max_power`,
`min_speed_mult`, etc. aren't sim-exercised per-club either).
