# Implementation Log — Multiplayer, Menu, Procedural Course, Lighting, Tests

Follow-up to [08_003.md](08_003.md).

## Automatic testing (now a real, permanent part of the repo)

- `scenes/tests/TestRunner.tscn` + `scripts/tests/test_runner.gd` — run it with
  `tools/run_tests.ps1` (or `.sh`), which locate the local Godot 4.7 exe
  (override with `$env:GODOT_BIN`/`GODOT_BIN`) and run headless, exiting 0/1.
  29 checks: pure unit tests for `CoursePath` (length, no-gap adjacency,
  checkpoint ordering), `GameManager` (turn advancing, checkpoint monotonicity,
  match completion), `ClubController.should_strike()` (the swing-gating
  decision logic, exposed as a static pure function specifically so it's
  testable without a live mouse), and one integration test that spins up the
  real `TestLevel` scene and drives the eraser through checkpoints/goal/a
  simulated fall.
- This suite **found two real bugs before you did**, both fixed and now
  permanently regression-tested:
  1. `LevelController._position_markers()` set `global_position` on
     Start/Checkpoint/Goal nodes from `_enter_tree()`, before those children
     had entered the tree themselves - `is_inside_tree()` failure, silently
     falling back to an identity-parent assumption that only happened to
     produce the right numbers because the level root sits at world origin.
     Switched to local `position` (correct regardless of nesting).
  2. The test's own fall-off-course point sat exactly on the floor's edge,
     missing the FloorSensor - a test bug, not a game bug, but worth noting
     since it's the kind of off-by-boundary mistake that's easy to reintroduce.
- Going forward: run `tools/run_tests.ps1` after any change to `GameManager`,
  `ClubController`, `CoursePath`, or level wiring.

## Procedural course (replaces the hand-built blockout)

- `scripts/levels/course_path.gd` (`CoursePath`, pure/no scene tree) generates
  a winding chain of platforms: each step's offset is chosen so its footprint
  is *guaranteed* to overlap the previous one (no impossible gaps, checked by
  the test above), while Z wanders sinusoidally (side-to-side) and Y steps up
  or down within a climbable range - both axes now genuinely vary, not just X.
- **Length x4** ("expand by 300%" = original + 300% = 4x): generation runs
  until cumulative path length passes `8.6m * 4 = 34.4m`; it lands around 41m
  including the Z/Y wander. Checkpoints are now placed at true 25/50/75% of
  *travelled path length* (not piece index), finally answering the "are they
  really equidistant" question left open in 08_002.md.
- `LevelController` builds this into an empty `Course` container node at
  runtime and repositions Start/Checkpoint1-3/Goal to match. Floor/FloorSensor
  were widened to `50m` to cover the longer course; two more furniture props
  were added further down (a second wall, extra fluorescent fixtures) so the
  back half of the course isn't in a void.

## Hotseat multiplayer

- `GameManager` now holds an array of `PlayerRun`s (name, strokes, checkpoint
  progress, respawn point, their ball's current resting transform) instead of
  single-player state, plus `active_player_index` and turn signals.
- Only **one physical Eraser exists** - it's teleported (via the existing safe
  `teleport_to()`) to whichever player is active. `scripts/levels/turn_manager.gd`
  watches for the eraser settling after a stroke and hands off the turn,
  skipping anyone who's already finished; when everyone's finished the match
  ends and the HUD shows a strokes-ranked summary.
- Trade-off, stated plainly: players don't see each other's balls
  simultaneously (there's only one on the course at a time) - much simpler to
  build and test than N simultaneous rigid bodies, but if you want everyone's
  ball visible at once that's a bigger follow-up (would need per-player Eraser
  instances and camera/turn logic to match).

## Main menu

- `scenes/ui/MainMenu.tscn` / `main_menu.gd` is now `run/main_scene`: title,
  a +/- player count (1-4), Start (loads `Main.tscn`), Quit. Player count is
  handed off via `GameManager.pending_player_count`, read by `LevelController`
  when it calls `setup_players()`.

## Whacker changes

- `ClubController` gates strikes on the left mouse button being held
  (`should_strike()`'s `button_held` param) - swinging near the eraser with
  the button up no longer does anything.
- Whacker mesh sits at 50% opacity normally, 100% while the button is held.
- The three whackers now behave like their golf namesakes instead of just
  differing in color: **Pencil/Putter** (low power, ~no loft, easy to
  trigger), **Pen/5 Iron** (balanced), **Toothbrush/Driver** (hits hardest and
  flattest, but needs the fastest swing - a half-hearted swing just won't
  connect). Numbers 1/2/3 still switch between them.

## Eraser speed

"Still moving too fast" after the earlier -80% max-power cut - the other half
of that equation is mass. `Eraser.mass` 0.15 -> 0.3 (half the velocity for the
same impulse) plus `linear_damp`/`angular_damp` set to 1.4 (it's a soft
eraser, not a marble - it should bleed off speed in the air, not just on
contact). Combined with the new putter/iron/driver `max_power` values (1.2 /
1.6 / 2.0, down from a flat 2.8), a full driver swing is now roughly a third
of last round's speed. Still worth a human playtest pass to see if it's right.

## Lighting

- "Reduce Global Illumination by 80%": the project renders in **GL
  Compatibility** mode (`project.godot`), which doesn't support SDFGI/VoxelGI
  - the only GI knob available is the environment's ambient sky light, so
  `ambient_light_energy` went `0.7 -> 0.14`. Flagging this so the interpretation
  is clear: if you later switch to the Forward+ renderer for real-time GI,
  this setting stops being the relevant one.
- Added dynamic, shadow-casting lights: a warm `OmniLight3D` lamp on the
  table, a flickering cool-blue light on the CRT TV
  (`scripts/environment/flicker_light.gd`), and three fluorescent tube
  fixtures spaced along the now-longer course. The directional "sun" light
  was left as-is (shadows were already on).

## Audio - what's real and what isn't

- `scripts/autoload/audio_manager.gd` (new `AudioManager` autoload) **does**
  work: it synthesizes short sine-wave SFX in code (hit/checkpoint/finish/
  turn-change/match-complete) as real 16-bit PCM `AudioStreamWAV`s at
  runtime - no external files, hooked to `GameManager`'s signals.
- **"High quality background music" was not built.** There's no
  music-generation tool available in this environment, and synthesizing
  simple tones is not the same thing as composed music - producing something
  and calling it "high quality" would be misleading, so I didn't. Options
  going forward: (a) you supply actual audio files and I wire up an
  `AudioStreamPlayer` for them, (b) you point me at a specific generation
  tool/service to integrate, or (c) I extend the current synth approach into
  a simple procedural ambient loop, which would be honestly described as
  "generated background tone," not music.
