## What got built

Nine low-poly, textured `.glb` models - one per `CoursePath.FLAVOR_NAMES`
entry (`Book`, `Ruler`, `StationeryTray`, `ToyBlock`, `BoardGameBox`,
`MugCoaster`, `RemoteBridge`, `Cup`, `Battery`) - authored entirely via
`execute_blender_code` (bpy) and exported to `assets/models/*.glb`:

- **Geometry** built from primitives + bevel modifiers, with one or two
  distinguishing low-poly details per flavor rather than plain boxes: a
  raised spine on the Book, a shallow inset cavity on the StationeryTray
  (bmesh `inset_region` + translate), four cylinder studs on the ToyBlock, a
  raised lid rim on the BoardGameBox, a rim ring on the MugCoaster, a grid of
  small button cylinders + a dark "IR window" band on the RemoteBridge, a
  tapered-cylinder profile on the Cup, and a cap nub + banded profile on the
  Battery. Poly counts stayed low (24-408 verts / 44-780 tris per object,
  RemoteBridge highest due to its 8 button cylinders).
- **Textures are procedural, not sourced** (per the explicit instruction
  this pass - external web textures are still deferred, not attempted here):
  each flavor gets its own 128x128 image painted directly in Python (a
  `hash01()` value-noise function plus per-flavor logic - tick marks and a
  red centerline for the Ruler, a page-edge-stripe + gold trim border for
  the Book, colored quadrants with black grout lines for the ToyBlock,
  concentric rings for the MugCoaster, a hashed color-cell grid for the
  BoardGameBox, banded silver/brass/green for the Battery, etc.), packed
  into the Blender file and embedded in the exported GLB - no network
  access, no image search, nothing outside this Blender session.
- **UV unwrap**: `bpy.ops.uv.cube_project` per object (deterministic, no
  manual seam work - acceptable for this style/scale of asset).

## The normalization trick that keeps the zero-gap/tilt invariant intact

This was the part that needed to be gotten right, not just "make it look
like a book" - 08_006/08_007 spent real effort getting pieces to touch with
*exactly* zero gap and capping cosmetic tilt + a 0.93 mesh shrink
specifically so a rotated visual mesh's corners can never poke past the
touching neighbor's seam (see `CoursePath` and
`LevelController._build_course_geometry`). Swapping the primitive `BoxMesh`
for a real modeled mesh could have silently broken that guarantee - a
non-box mesh's corners could, in principle, sit anywhere.

The fix: every exported mesh is built at (approximately) its real target
proportions from `CoursePath.FLAVOR_SIZES`, then in a final Blender-side
step its vertices are recentered and **rescaled per-axis so the mesh's
bounding box is exactly `1x1x1`, centered on the origin** - regardless of
bevel/detail overshoot. `LevelController` now scales each
`MeshInstance3D` by `piece.size * 0.93` (was: a `BoxMesh` sized to
`piece.size` with a uniform `0.93` node scale). Because a mesh's furthest
vertex can never exceed its own bounding box, and that box is now exactly
`piece.size * 0.93` after the node scale, the worst case is identical to
the old axis-aligned box case - the safety argument the earlier sessions
relied on carries over unchanged, just generalized from uniform to
per-axis scale.

## Code changes

- `CoursePath.Piece` gained a `flavor: String` field, set at construction
  from `FLAVOR_NAMES[flavor_i]`. This was needed because the *last* piece's
  `piece_name` gets overwritten to `"GoalPad"` (goal marker) - without a
  separate field, `LevelController` would have had no way to know which
  model the goal piece should actually use.
- `LevelController` gained `FLAVOR_MODELS` (9 `preload()`s of
  `res://assets/models/*.glb`) and `_get_flavor_mesh()` /
  `_find_mesh_instance()` helpers that instantiate a flavor's imported
  scene once, pull out its `Mesh` resource, and cache it (keyed by flavor,
  not by size, since the same normalized mesh now serves every size via
  scale). `_build_course_geometry()` uses the real mesh + per-axis scale
  when a flavor has a model, falling back to the original primitive-`BoxMesh`
  + flat-color path for any flavor that doesn't (none currently, but keeps
  the code non-fragile if `FLAVOR_NAMES` grows before a model is added).
- Material handling: the old per-piece `material_override` (flat
  `piece.color`) is skipped for real models - the glTF-imported material
  (with the baked albedo texture) is used as-is. Pillars still use
  `piece.color` (unchanged, still primitive cylinders).
