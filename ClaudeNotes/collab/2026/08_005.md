# Implementation Log — Building-Block Course Rewrite, Multiplayer Polish, Testing

Follow-up to [08_004.md](08_004.md). This single session covered a very large,
rapid-fire batch of requests; grouped by theme below. All of it is validated
by `tools/run_tests.ps1` (44 automated checks, 0 failing at the end of this
session) plus a real windowed playtest via the local Godot 4.7 exe.

## Multiplayer: real simultaneous balls, not a shared teleported one

08_004 shipped hotseat multiplayer with one physical ball teleported between
turns. That's gone: **each player now has their own real `Eraser` instance**,
spawned together at Start, each a distinct color
(`GameManager.PLAYER_COLORS`). Two things fall out of that:

- **Spawn collision guard**: stacked-at-the-same-point erasers would
  otherwise shove each other apart on the first physics tick. Each Eraser
  starts with `collision_layer/mask` limited to the course only
  (`Eraser.begin_spawn_guard()`); once it's physically moved
  `spawn_guard_distance` (0.3m) from the start point, it rejoins normal
  eraser-vs-eraser collision. Regression-tested.
- **Turn-start popup buffer**: `scenes/ui/TurnPopup.tscn` dims the screen and
  shows "Player N's turn" with a Start Turn button between every turn (and
  before the first). `GameManager.turn_ready` gates
  `ClubController.should_strike()` - no swing lands until the popup is
  dismissed. `TurnManager` (`scripts/levels/turn_manager.gd`) is now much
  simpler: no teleporting, just watch the active player's ball settle after
  a stroke, hand off to the next unfinished player, retarget camera/club.

## Camera: rotate + zoom

`CameraRig` (`scripts/player/camera_rig.gd`) now supports **middle-mouse-drag
to orbit** horizontally around the ball (elevation angle stays fixed at 45°
per spec) and **mouse-wheel to zoom** (`zoom_min`/`zoom_max` clamp it).
`snap_to_target()` is used on turn changes so switching players doesn't slow-pan
across the whole course.

## The course generator was rewritten from scratch (twice, honestly)

This is the big one, and the automated **playability test** (see below) is
what made it possible to actually get right instead of shipping something
that only looked fine.

- **Objects are real building blocks now**: "should not overlap each other"
  meant abandoning the earlier guaranteed-overlap approach entirely. Each
  next piece is placed touching the previous one with **zero gap and zero
  overlap**, computed via the correct box-to-box touching-distance formula
  along the direction of travel (`CoursePath._touch_distance()`). Getting
  this formula right took two attempts - the first version used each box's
  *support distance* (farthest-point-in-a-direction), which only equals the
  correct touching distance for two equal-sized square boxes at exactly 45° -
  everywhere else it silently left gaps up to 0.4m. The corrected formula
  (ray-exit distance from the combined half-extents box) gives an exactly
  measured **0.000m** max separation across the whole generated course now
  (see the automated test).
- **A rotated bridge plank spans every seam** (`LevelController._add_bridge`,
  0.9m wide, padded to rest generously onto both blocks) - since the blocks
  themselves never overlap, the bridge is the actual guaranteed-walkable
  surface and the "improvised plank across a gap" visual the brief asked for.
  It's built from the exact 3D vector between piece centers via
  `Basis.looking_at()`, so it's tilted in whatever pitch+yaw the terrain
  actually needs - real "variety of vertical and horizontal angles."
- **Real winding, minigolf-style routing**: the path now follows a heading
  that turns 25-55° left or right every 2-4 pieces (with a gentle pull back
  toward straight-ahead so it still makes net progress, and soft steering to
  stay inside the room's walls) instead of a gentle sine-wave wobble. This is
  a heading-based generator, not just an X-axis crawl with Z jitter.
  ("400% more winding" was the ask; there's no precise way to measure that
  multiplier, but the qualitative character changed from "wobbly corridor"
  to "real doglegs.")
- **Realistically sized objects**: household object sizes were increased
  substantially relative to the eraser (~0.35m) - a Book is now 2.2m long, a
  BoardGameBox 2.4m, etc. - so they read as genuinely bigger than the eraser
  the way a real book dwarfs a real eraser. A **Battery** flavor was added,
  deliberately kept eraser-scale (0.45m) per the explicit ask.
  These are still primitive boxes/cylinders with distinct colors, not
  textured models - see the "what I can't do" section below.
- **Length -50%**: `LENGTH_MULTIPLIER` 4.0 → 2.0 (the earlier "expand by
  300%" pass); the generated course now targets ~17m of actual path length.
- **Step height is bounded by the piece's *top surface*, not its center** -
  pieces vary in thickness (a chunky ToyBlock vs. a thin Ruler), so bounding
  center-y alone let the real, physically-relevant ledge height between two
  different-thickness pieces run well past the intended limit. This was the
  second real bug the playability test caught.
- **Cosmetic-only rotation for the "kid-built" look**: every piece's visual
  mesh gets a small random tilt (`Piece.visual_tilt_deg`, seeded) applied as
  a child transform - the collision box underneath stays perfectly
  axis-aligned at the tested, guaranteed-safe footprint. Pitch/roll ±6°, yaw
  ±12°. Decorative pillars (`_add_pillar`) run from each elevated piece down
  to the floor for a "propped up" look, colored per-piece, no collision.
- **The floor is lava**: `scripts/environment/lava_floor.gd` pulses a
  dark-red emissive material; `FloorSensor` (unchanged from earlier) is what
  actually resets the eraser to its last checkpoint on contact - already
  true before this session, now visually sold. Course pieces are kept well
  above it (`MIN_CENTER_Y = 0.4`, hard-clamped, not just reflected) so the
  course never dips to floor level.

## The playability test (and what it caught)

`_run_playability_test()` in `scripts/tests/test_runner.gd` drives a
simulated player through the **real, generated** course using **real**
physics: it aims at the next piece ahead (not a distant checkpoint - a
"nearest piece, searched only forward" tracker was needed since the path can
now pass close to its own earlier stretch), picks power proportional to
distance the way a competent player would, adds aim jitter, and strikes via
the real `Eraser.strike()`. It's genuinely useful, not decorative - across
this session it caught, in order:

1. A `global_position` set on a not-yet-in-tree node during `_enter_tree()`
   (silently no-op'd, worked by luck since the level root sits at the world
   origin) - fixed to use local `position`.
2. **A real race condition**: `Eraser.teleport_to()` zeroes velocity
   synchronously but only clears `freeze` a physics frame later;
   `is_settled()` used to read "true" (zero velocity) during that gap, so a
   strike landing there was silently dropped by the physics server. Now
   `is_settled()` stays false for the whole teleport, not just until
   velocity hits zero - a real gameplay bug (imagine trying to swing right
   after respawning, having it not surface a physical reason why nothing
   happened), not just a test artifact, and now permanently regression-tested.
3. My own test had an ordering bug (checking `is_settled()` before waiting a
   physics frame for the impulse to be integrated) that looked identical to
   the class of bug above - worth flagging since it cost real time to tell
   apart from an actual gameplay issue.
4. The touching-distance math error described above.
5. The step-height-by-center-not-top-surface issue described above.

Tuning that came out of getting this test to actually pass: gentler max step
height (0.15 → 0.08), gentler turn angles (35-80° → 25-55°), wider/more
generous bridge planks, and eraser friction 2.2 → 1.6 (still "high friction"
relative to the room, just no longer so grippy it could grind to a near-halt
on the many more numerous seams a shorter, more tightly-packed course now
has). Final result: **103 strokes** to complete the generated course with a
realistic simulated player - passes with room to spare under the 120-stroke
budget.

## Speed, lighting, and other direct requests

- **Speed doubled**: whacker `max_power` values doubled again (putter 1.2→2.4,
  iron 1.6→3.2, driver 2.0→4.0).
- **GI removed / lighting moodier**: `ambient_light_energy` → 0.0 (the
  project renders GL Compatibility, which has no SDFGI - this was already
  the only real GI knob, see 08_004). The directional "sun" light (not
  really motivated in a windowed-out house anyway) is down to 0.12, kept
  only so nothing goes pure-black between practical lights. Practical
  lights - the table lamp, the flickering CRT glow, three fluorescent tube
  fixtures - are the real illumination now, and were pushed brighter for
  contrast against the darker base.
- **Fully enclosed house**: 4 walls + a ceiling, sized to the floor
  (`WallNorth/South/East/West`, `Ceiling`, all with real collision).

## What I can't actually do here (said plainly, not worked around)

- **Textured 3D models**: there's no 3D-asset-generation tool available in
  this environment. What shipped instead is the best available substitute -
  bigger, better-proportioned primitives (boxes, tapered cylinders for
  cups/mugs), distinct per-flavor colors, and the cosmetic tilt for visual
  chaos - but it's still primitives, not textured meshes that actually read
  as "a paperback book" up close. If you have real model files (.glb/.gltf
  with textures) I can wire them in per flavor; otherwise this needs an
  external modeling/asset pipeline I don't have access to.
- **Real composed background music**: unchanged from 08_004 - SFX are real
  (synthesized in code), music was not faked.
